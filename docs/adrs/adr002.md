## arc42-Architekturbeschreibung: SVWS-Konferenzübersicht

**1. Einführung und Ziele**

Das Tool ermöglicht Lehrkräften und Schulverwaltungen eine digitale Notenkonferenzübersicht für Klassen und Lerngruppen. Es läuft vollständig im Browser (Single-Page-Application), benötigt keine serverseitige Installation und kann optional auf einen SVWS-Server zugreifen.

**2. Randbedingungen**

- Deployment: Statische HTML/JS/CSS-Dateien, keine Backend-Infrastruktur nötig
- Datenformat: Gezipptes JSON (SVWS-Exportformat)
- Zwei Datenbezugswege: REST-Abruf (online) + manueller Upload (offline)
- Datenschutz: Keine Übertragung an Drittserver; alle Daten bleiben im Browser

**3. Kontextabgrenzung**

Hier ist die Systemkontextübersicht:**4. Lösungsstrategie**

- Reine Client-Side-App (Vanilla JS oder leichtes Framework wie Svelte/Vue)
- Datenverarbeitung komplett im Browser via `fflate` (WASM-freies Unzip) + JSON.parse
- Keine Cookies, kein Login, keine persistente Speicherung sensibler Daten
- Druckoptimiertes CSS für die Konferenzansicht

**5. Bausteinsicht**

Hier die interne Komponentenstruktur:**6. Laufzeitsicht — Datenladesequenz****7. Verteilungssicht**

- Deployment als statische Dateien: Webserver (nginx, Apache), GitHub Pages, oder einfach `index.html` per Doppelklick öffnen
- Keine Abhängigkeit zu Backend, Datenbank oder Node.js
- CORS-Konfiguration am SVWS-Server notwendig (nur für REST-Modus)

**8. Querschnittliche Konzepte**

| Thema | Lösung |
|---|---|
| Datenschutz | Alle Daten bleiben im Browser-Speicher, kein Drittserver |
| Barrierefreiheit | Semantisches HTML, ARIA-Labels, Druckstylesheet |
| Fehlerbehandlung | Validierung des JSON-Schemas vor Darstellung |
| Offline-Fähigkeit | File-Upload-Pfad vollständig ohne Netzwerk |
| Druckbarkeit | `@media print` CSS für A4-Ausgabe |

**9. Architekturentscheidungen (ADRs)**

- **ADR-01**: Kein Framework-Zwang — Vanilla JS oder leichtgewichtiges Framework (VUE empfohlen), um Deployment ohne Build-Pipeline zu ermöglichen
- **ADR-02**: `fflate` als ZIP-Bibliothek — rein clientseitig, keine Serverabhängigkeit, 9 kB gzip
- **ADR-03**: Kein persistenter Datenspeicher — Datenschutz-by-Design; Daten existieren nur für die Browsersitzung

### Prompt-Plan für die KI-gestützte Entwicklung

**Prompt 1 — ZIP-Parser (Fundament):**
```
Du entwickelst eine Browser-SPA ohne Backend.
Schreibe eine ES-Modul-Funktion `parseZippedJson(input)`,
die entweder ein ArrayBuffer (aus fetch) oder ein File-Objekt (aus Input)
entgegennimmt, mit der Bibliothek `fflate` entpackt
und das enthaltene JSON als JavaScript-Objekt zurückgibt.
Fehler sollen als sprechende Exceptions geworfen werden.
Keine externen Abhängigkeiten außer fflate (CDN-Import).
```

**Prompt 2 — Datenmodell:**
```
Gegeben ist folgendes SVWS-JSON-Schema: [Schema einfügen].
Erstelle ein JavaScript-Datenmodell (plain objects, kein TypeScript),
das Klassen, Schülerinnen und Schüler sowie Fächer mit Noten
in einer für die Tabellenansicht optimierten Struktur speichert.
Erstelle außerdem eine Validierungsfunktion, die prüft,
ob alle Pflichtfelder vorhanden sind.
```

**Prompt 3 — Klassenübersicht-Tabelle:**
```
Erstelle eine Web-Komponente / Funktion `renderClassView(classData)`,
die eine HTML-Tabelle erzeugt:
- Zeilen: Schülerinnen und Schüler (Nachname, Vorname)
- Spalten: alle Fächer der Klasse
- Zellen: Zeugnisnote, fehlende Noten als leere Zelle markiert
- Markierung von Noten unter 4 (rot) und "nicht erteilt"
- Druckoptimiert: kein JavaScript für @media print nötig
```

**Prompt 4 — Ladeoberfläche:**
```
Erstelle die Startseite der SPA mit zwei klar getrennten Bereichen:
1. REST-Modus: Eingabefeld für SVWS-Basis-URL + Klasse/Token,
   Laden-Button, Statusanzeige (lädt / Fehler / Erfolg)
2. Offline-Modus: Drag-and-Drop-Bereich + klassischer Datei-Upload
   für eine .zip-Datei
Kein Framework, kein Build-Schritt — reines HTML/CSS/JS.
```

**Prompt 5 — Gesamtintegration:**
```
Verbinde die Module rest-loader.js, file-loader.js, zip-parser.js,
store.js und die Views zu einer funktionierenden SPA in index.html.
Alle Module als ES-Module per <script type="module">.
Die App soll ohne Build-Schritt im Browser funktionieren
(kein Webpack, kein Vite).
```

### Empfehlungen für den Start

Zunächst solltest du das SVWS-JSON-Schema genau dokumentieren — das ist die kritischste Abhängigkeit. Ohne bekanntes Schema können Parser und Datenmodell nicht korrekt entwickelt werden. Am besten legst du eine echte (anonymisierte) Testexportdatei ins Repository.

Als Technologie-Stack empfehle ich **Vanilla JS mit ES-Modulen** für maximale Deploybarkeit. Wenn später mehr Reaktivität gewünscht wird, lässt sich VUE (mit Vite Build) einfach nachrüsten, ohne die Architektur zu ändern.
